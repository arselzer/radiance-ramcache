RAM expert cache: prefill strategy and measurement gates
2026-10-25. Design/working note only. No implementation or performance claim.

The current closed GLM correctness fixture is T5/R2/E4/top2/TP1. Its source has
24 owned records and8 ordinary resident expert0 records. HOT holds65536B, COLD
98304B and three reusable GPU consumers plus sentinel charge196608B. The Core
requires the entire selected current-slice union ready before GU. A RAM HOT hit
avoids payload file reads, but still uploads the selected expert into a new GPU
consumer generation. This is not a persistent GPU expert L1 and not a measured
large-prompt configuration. Actual code: core/runtime/expert_prepare.cpp,
core/place/native_mover.cpp and the native source/owner prototypes.

Expected workload distinction
Prefill usually selects more distinct experts, so a small RAM cache may see a
near-scan workload. It can nevertheless amortize each expert upload across many
tokens assigned to that expert. Decode needs fewer experts per step but has far
less arithmetic to hide their transfer latency. Therefore no unmeasured claim
that prefill's relative slowdown is always larger than decode's is justified.
When consecutive prefill chunks sweep an expert working set larger than the RAM
cache, repeated SSD reads can dominate. Cache replacement cannot remove that
bandwidth lower bound. Quant size increases bytes per miss and reduces both RAM
and GPU coverage; aggregate memory capacity alone does not establish usable speed.

Implementation sequence after correctness and Engine source authority
1. Measure actual routes, unique expert bytes and requested/uploaded bytes per
   layer/chunk, RAM HOT/COLD hit/miss/eviction/bypass counts, disk bytes and time,
   H2D bytes and checked readiness time, GU/activation/DN time and idle gaps.
   Separate disk cache from OS page cache, source setup from routed demand,
   prefix-cache hits from real prefill, and fixed GPU residents from RAM hits.
2. Within an explicitly admitted general profile, group token work by expert and
   choose a larger route window only when the selected union fits its consumer
   and COLD credits. Larger windows trade activation memory for expert reuse.
   The current fixed R2 profile is deliberately not adjustable with serving flags.
3. Add expert-batch streaming if a useful window's full selected union exceeds
   consumer capacity: prepare a bounded expert run, compute all corresponding
   GU/nonlinearity/DN rows, retain the correct original token/slot outputs, retire
   after true readers, then reuse slots. Publish the layer result only after all
   required runs finish. Preserve route/drop semantics and original per-token
   accumulation/rounding order; expert reordering must not silently change gather.
   This changes the current whole-union contract and needs a distinct capability,
   budget, failure protocol and independent end-to-end tests.
4. Overlap subsequent source reads and uploads with already-ready computation,
   using separate credited buffers and generations. No consumer overwrite while
   queued readers remain, no asynchronous work referring to expired source spans,
   no READY before checked events. A semantic error must stop later submissions
   and retire all involved streams before releasing any landing/cache backing.
5. Add scan-resistant RAM admission for prefill (e.g. first-touch bypass or
   bounded probation/feedback), protecting repeatedly useful decode experts.
   Compare policies on fixed route traces; do not assume locality or pin entire
   recently scanned layers without measuring the byte/hit tradeoff. A persistent
   GPU hot set is a separate optional layer requiring its own eviction/readiness
   design; it is not supplied by the current Native consumer mechanism.

Comparative tests, once a real-model path is authorized
Cold unique prefill, warm repeated-route prefill without prefix reuse, realistic
long conversations with prefix reuse reported separately, decode at matched
content/length/MTP settings, and mixed prefill+decode at matched concurrency.
Report both throughput and latency percentiles, disk/H2D bytes per prompt and per
output token, cache coverage in BYTES, transferred unique/duplicate expert bytes,
and memory reservations/observed peaks. Include a full-working-set scan larger
than RAM and an adversarial no-locality trace. Larger quants need separate
encoding/kernel correctness and measurements; this design does not enable them.
No production configuration, restart or unapproved full-model conversion follows
from this note. The current next gate remains the tiny native-owner GPU checker.
