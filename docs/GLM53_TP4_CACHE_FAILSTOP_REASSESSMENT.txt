TP4 cache first-profile scope reassessment,2026-10-25

The earlier GLM53_TP4_CACHE_PREPARE_COORDINATION_DESIGN describes the stronger
graceful-return/retirement problem. Parent narrowed the FIRST experiment to a
cache-specific PROCESS-FAIL-STOP policy, following the existing tiny retirement
precedent. A complete generic collective transaction framework is therefore
NOT a prerequisite for this first cache coordinator prototype.

Concrete NEW source package:
glm53-tp4-cache-prepare-coordinator-prototype
Its fixed four-rank enter and ready gates surround local cache work before GU.
Known cache/metadata/early-rank failure notifies peers and the actual intended
adapter MUST take fixed _Exit(88) before returning into Engine cleanup/drains.
Returning statuses exists to inspect the standalone HOST state machine; it is
not proposed recoverable whole-Engine handling. Current Native/Permanent TP1
guards remain unchanged, and the prototype advertises no Core/serving capability.

Specific readiness clarification from active source:
runtime/issue.cpp344 sync_residency only queues table-change bookkeeping; it
does not complete H2D or enqueue readiness waits. native_mover.cpp120-162 uploads
and records an event; record_residency.cpp102-140 publishes WeightSlot ready
handles. Ctx::resolve_weight (issue.cpp76-109) normally enqueues the checked
event wait later at GU operand resolution. Thus a future preGU READY vote must
either complete the actual upload event first (simplest correctness baseline),
or establish checked same-stream readiness with retained leases explicitly.
owner.prepare==OK +sync_residency is NOT an independent completed-copy proof.

If a pre-existing GPU/collective hang never reports a host error, a CPU gate
cannot wake it. The process-fatal profile does not solve that class or promise
safe device teardown/recovery. If a known error is reported before a rank reaches
prepare, the Engine/Ctx guard must fail-stop immediately rather than waiting for
the other rank's stream. OS/driver cleanup of a process with in-flight work is
outside the CPU subprocess proof. Graceful recovery would require additional
work; do not force that broader objective into this first scoped cache test.

No active Core changes, compiler, numerical/model/GPU execution or network used.
