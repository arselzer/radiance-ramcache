The observed V2 owners==4 failure is explained by the checker schedule, without
evidence of a Core protocol defect. Coordinator::enter first agrees all rank IDs.
Before every waiting caller resumes, a fast rank can ready(E_IO). Slower callers
then correctly observe sticky failure and skip owner work. This is valid fail-fast
behavior, so ID agreement alone cannot establish that all four caller counters
have incremented before the injected fault.

V3 adds a TEST-ONLY post-enter rendezvous for that late-source case. All four
workers must return successfully from enter and increment owners before rank3
injects its READY failure. The waiting gate has a monotonic deadline and observes
coordinator failure; timeout reports failure to wake peers. The strict owners4,
one injection, first E_IO and no-GU requirements remain in place.

Review found an additional checker false-positive path: the generic watchdog
also injects E_IO, so its rescue could conceal a broken notification. V4 records
watchdog firing before the rescue and requires it never fired after workers and
watchdog have joined. It additionally requires the first failure's source_failure
reason and rank3 attribution. A watchdog rescue cannot count as test success.
