# Exact optimizations, ranked: research of 3 November 2026

Workflow wf_2693fd62-a3f (inventory of prior trials, four lenses, adversarial verification). 18 candidates
reached verification: 10 on concurrency and prefill (group A) and 8 on latency, speculation, system and
upstream (group B). 10 are kept and ranked below, and 8 are dropped. No kept item touches weights, routing,
arithmetic or reduction order. Each one changes scheduling, residency, I/O, clocks or issue order, so replies
stay byte-identical to the base engine.

**How the claims were checked.** The verifiers compared each claim with Window CW (ab-20261103T090558Z), the
stable Qa0 server log, the post-move BWMix reading and the current source (decode-impl 1c0a01b3, runtime
e184c6b7). They also replayed the Oct 29 route traces offline, on the CPU only. No GPU work, build or server ran
for this report. Gains are estimates unless they are marked as measured, and a replay is not an engine
measurement. Engine paths are relative to `/home/as/radiance-ds41-claude`.

**Configurations.** R is the recommended configuration (Lc2048 + P1 + lent arena). C2 is R + Rb + Vp, which is
being adopted. C4 is Lc4096 + Pci4096 + Rb + Vp.

**Baseline.** In CW (four XTs, fresh servers), total decode at N4 / N8 is 37.4 / 41.3 tok/s for R and
38.1 / 41.8 for C2. One stream runs at about 29-31 tok/s. Under R, Ulong prefill takes 1.9 / 4.2 / 7.4 s for
82 / 933 / 3,086 tokens. The quiet stable Qa0 study (PREFILL-QA0-20261103.md) gives 7.65 s for 3,086 tokens
(403 tok/s) and 10.82 s for 6,817 (630 tok/s). The 500 tok/s target is therefore now missed mainly at 2-4K
tokens, where the prompt's last chunk dominates: at 3,086 tokens it takes 5.00 of the 7.22 s of chunk time.

**Ranking method.** Each candidate is ranked by its expected gain on the user's priorities, times its chance of
passing the first gate, divided by its effort. The priorities, in order, are concurrent decode throughput,
long-prompt prefill and harness turns. GPU-window arms count as the scarce resource. Effort sizes are S (up to
a day), M (2-5 days) and L (1-3 weeks).

## Kept candidates

### 1. Fill the RAM cache to capacity at startup (A2)

- **Mechanism.** The adopted CACHE_WARM warms only units with profile_share > 0 (`core/place/stager.cpp:4100`).
  In CW C2 the ranks warmed 2,310 / 2,294 / 2,263 / 2,268 units into 2,848 slots per class, so 538-585 slots per
  rank started empty. The fresh servers then missed 354 / 342 / 392 / 371 times with 0 evictions, and 203-222
  slots were still empty when the arm ended. The fix fills those free slots with zero-decode units. They are
  inserted before the hot units, so LRU evicts them first. The fill takes units in prefill-count order from the
  sealed profile (3,526 zero-decode units, 1,187 of them with prefill counts), then in layer/expert order.
- **Gain (corrected).** The offline replay predicts 337 / 326 / 373 / 370 cold misses per rank, within 5% of the
  measured counts. After the fill it predicts 85 / 74 / 85 / 79 (−76%).
  - Fresh-server N4/N8 harness +3-9%: decode_tps +3-8%, and the 8 short prefills finish 0.6-1.1 s sooner.
  - Steady state: about 0, because the cache fills itself within about 15-40 requests. Most of the measured
    gain will be a cold-start penalty that today's fresh-server arms include.
  - Startup: about +6 s (about 37 GiB more read at about 6 GiB/s, with the ranks warming one after another).
  - It also makes rank 4's batched pass CPU-bound instead of drive-bound.
- **Exact.** Yes. It changes residency only, and uses the same insert path and scale round-trip gate as today's
  warm.
- **First step.** In `hx_warm`, after the profile list, add the eligible zero-share units (prefill-count order,
  then layer/expert order) ahead of the hot ones, and log the units by source and the seconds taken.
  - Only decode shares reach the plan today (`core/place/planner.cpp:427-436`), so prefill-count order needs the
    profile's `counts.prefill` passed into the plan.
  - Layer/expert order alone fills the same slots but saves fewer misses. An untested estimate: roughly the
    slot-coverage fraction, 60-65% instead of 76%.
  - Window: C2 N4/N8 with the fill off and on, on fresh servers, plus a warm-server second wave as the
    steady-state control. Gate: at most 150 misses per rank, and identical replies.
- **Effort.** S: half a day to a day plus a host test, and 2-3 arms.
- **Files.** `core/place/stager.cpp:4095-4140` (`FileStager::hx_warm`); `core/place/planner.cpp:427-436` and
  `planner.h:79` (the profile share; a prefill share would be new); the README entry for
  `RADIANCE_EXPERIMENTAL_DS41_CACHE_WARM`.
- **Risk.** Low. The 192 GiB eviction path becomes active from the start; it is rarely exercised in short arms.
  The fill pins no extra memory, because `pregrow` already pins every slab at startup.

### 2. Pin the four XTs' DPM clocks; check power caps for prefill (B5)

- **Mechanism.** All four XTs run at performance level `auto` with the `BOOTUP_DEFAULT` profile (sysfs). KFD does
  not switch them to the COMPUTE profile by itself. During decode the cards wait about 0.4-3 ms per layer for the
  CPU pool. If the SMU lowers the shader or memory clock in those gaps, every burst starts slow.
  - Rank 0's card chain grows 2.75x from N1 to N8 (0.50 → 1.38-1.43 ms per layer in CW). A clock drop is one
    possible cause; kernels that scale with rows and skew between ranks are others.
  - GPU clocks were never tested. The earlier power arms (+0.4-0.6%, within noise) changed only the CPU governor,
    the NVMe latency tolerance and the C2 idle state.
  - Power caps: 03 and 83 at 304 W, 48 and c6 at 317 W; the maximum is 340 W on all four.
- **Gain (corrected).** 0 if the burst clocks already run at the top. Otherwise about +3-9% at N8 and +2-5% at
  N1. The power caps matter only if 03 and 83 show power-throttle bits during P1 waves (prefill).
- **Exact.** Yes. Clocks do not change arithmetic. The engine's run-to-run byte identity (identical replies at
  N1, N4 and N8) already rules out timing-dependent reductions, and the reply gate still applies.
- **First step.**
  - Add the four XTs' `power_dpm_force_performance_level` files to ab_window.sh's `POWER_FILES` save/restore,
    as a new power letter beside `Q[gnc]` (for example `Qd`). Resolve the files from the fresh UUID→BDF map
    (03, 48, 83, c6) and never touch the R9700 at c3. Every exit path restores `auto`.
  - Run a read-only `gpu_metrics` sampler (world-readable, 20-50 Hz) during all arms. It can refute a clock
    drop but cannot resolve 1-5 ms bursts.
  - Pair: C2 N8 against C2 N8 + Qd. Compare decode_tps and rank 0's counts-wait line ("waited ... us a layer").
  - Optional: a COMPUTE-profile arm (`pp_power_profile_mode` 5).
  - This is a system-wide setting, so ask the user first, as for the earlier governor arm.
- **Effort.** S: 2-4 hours of script and 2 arms.
- **Files.** `tools/ds41-host-experts/ab_window.sh:228-262` (`POWER_FILES`, `power_set`, `power_restore`) and
  `:1995` (the `Q[gnc]` arm part); a new read-only sampler script in `/home/as/ds41-claude-build/work/`.
- **Risk.** Low, provided `auto` is restored and c3 is never written.

### 4. Admit a wave's short prompts in one prefill step (A1)

- **Mechanism.** With LCP and more than one sequence, the scheduler requires PREFILL_ALONE
  (`core/sched/scheduler.cpp:112`), which admits one entry per step (`:2982`).
  - A wave of N short prompts is therefore prefilled in N consecutive steps. Each step holds every decode row,
    and each pays for the union of experts its own prompt touches.
  - CW C2 N8: 8 prefill steps take 5.28 of 15.22 s, with TTFTs of 0.90 ... 5.28 s, and 63 decode steps average
    157.7 ms at 7.59 rows. N4: 5.14 of 16.46 s.
  - The fix admits several whole short prompts in one prefill-only step: at most 256 rows, so the lent arena
    above the 256-row level stays lent; no decode rows; P1 not armed (it starts at 320 rows).
- **Gain (corrected).** Replay of the held-out route trace (the same 8 prompts), in non-resident expert-passes:
  - separate prefills: 16,457;
  - one batched pass: 6,561 (−60%);
  - the 6+2 split that the 256-row cap forces: 8,890 (−46%);
  - N4's 4+4 waves: 9,290 (−44%).

  For bursts of short prompts that arrive together, this gives N8 harness +12-18% (the uncapped bound is +23%),
  N4 +13-17% and a wave wall time 10-20% shorter. The first TTFT rises by 1.4-2.3 s, and the last falls by 2-3 s.
  - Server decode_tps does not change. Most of the harness gain comes from how the metric is computed: it counts
    the other prompts' prefill steps inside each stream's decode interval.
  - Staggered arrivals and long prompts: about 0.
  - Without rank 1 the batched pass is drive-bound (about 870 cold units touched across ranks): about 2.3-3.2 s
    for 8 prompts, against 5.28 s now.
  - Drop the proposed second phase with decode rows riding along: about +45 ms per short prefill, under 1%.
- **Exact.** Probably.
  - Heights up to 256 already run per op with the same per-row arithmetic, and a row's result does not depend
    on the other rows of its pass.
  - A shared step only changes work and caching. It runs consumer skip on every layer (the existing rule),
    which by the cone formula adds only 2.5-10% layer-rows at 82-933 tokens. It also admits every unit to the
    cache.
  - Risk: tall passes (17-256 rows) that hold several sequences have never run, because the scheduler forbids
    them. The attention, compressor, indexer and Engram cu paths are unexercised there, and the per-row cut code
    assumes one sequence. Upstream b264e9bd fixed this class of bug in another kernel: a row's rounding depended
    on which rows shared the launch.
  - Gates: Kh of each prompt batched against alone, N4/N8 reply identity, Kld.
- **First step.**
  - CPU only: sched_test cases for the switch. Cover several whole short prompts in one prefill-only step (at
    most 256 rows, no decode rows, P1 unarmed), cancelling one of them, and replan or preemption with several
    prefill entries. Audit every one-sequence assumption on the 17-256-row paths in `arch/deepseek41` and the
    stager.
  - Then one window, after rank 1 if possible: Kh of the 8 held-out prompts batched against alone, and C2 N4/N8
    with the switch off and on. Watch steps_prefill (8 should become 1-2), decode_tps (within ±1%), the harness
    rate, the wave wall time and the TTFTs.
- **Effort.** M: 3-5 days (the switch about 1 day, the audit and fixes 1-3, tests 1), plus one window.
- **Files.** `core/sched/scheduler.cpp:112`, `:2982` and the replan, preempt and cancel paths;
  `core/sched/batch.cpp`; `core/sched/consumer_skip.h`; `core/place/stager.cpp` (the LCP admission row and the
  per-row cut); `arch/deepseek41/deepseek41.cpp` (cu paths at 17-256 rows); `tests/sched_test.cpp`,
  `tests/consumer_skip_test.cpp`, `tests/ds41_consumer_skip_arch_test.cpp`.
- **Risk.** Medium: unexercised multi-sequence tall paths, and a later first token for the first prompt.

### 5. Carry each prompt's P1 drive units across its chunks (A6)

- **Mechanism.** Phase 1 reads non-admitted drive units read-only in every 2,048-token chunk, then frees them.
  The next chunk of the same prompt reads many of the same units again.
  - `add_drive` already sends a landed unit straight to the packer (`core/place/card_expert_stager.cpp:894-915`).
    A per-prompt store of landed planes therefore removes the re-reads. Cap the store from MemAvailable, and
    release it at the prompt's end or on cancel.
  - Qa0 log, 3,086 tokens: 1,040 rows / 21 layers / 138 units / 2.22 s, then 2,032 rows / 37 layers / 303 units /
    5.00 s.
  - Qa0 log, 6,817 tokens: 81 / 116 / 115 / 241 units in 1.19 / 2.40 / 2.66 / 4.45 s.
  - The issuing thread waited 4.84 s for drive units in 17.92 s of chunks, about 4.9 ms per unit.
  - This is the I/O half of the blocked Phase 2, without persistent activations. It differs from d0f (reuse of
    card copies) and from SIDE_STORE (refused inserts, CPU path only).
- **Gain (corrected).** Replay of the Oct 29 Ulong trace at C=2048, end-aligned: 733 of the final chunk's 1,524
  drive units (48%; rank 0: 177 of 385) had already been read in chunk 0, and 86% of chunk 0's set recurs. That
  passes the 30% kill gate.
  - At Qa0: 3,086 tokens 0.6-1.1 s faster (−8 to −14%); 6,817 tokens 1.2-2.4 s faster (−11 to −22%). The 6,817
    figure is extrapolated, because no 6.8K trace exists.
  - Prompts of 2,048 tokens or fewer, and N4/N8 decode, are unchanged.
  - This is the lever for the 2-4K range, which still misses the target: 3,086 tokens run at 403 tok/s and need
    about −19% to reach 500.
- **Exact.** Yes. The same container bytes give the same packer output. Check the container epoch before
  reusing planes.
- **First step.**
  - Capture a 6,817-token route trace (measure-first item 4) and rerun the overlap replay
    (`/tmp/claude-verify/cand6.py`). This replaces the proposed log-only counter window.
  - Then build the capped store with `p1_stager_test` cases. Holding the whole overlap needs 140-170 units per
    rank (2.6-3.2 GB per rank, 11-13 GB in total, against 34-41 GB MemAvailable at 192 GiB). A cap of 96 units
    per rank is safer. Untested estimate: it holds about 55-70% of the overlap, so expect the lower part of the
    range.
  - Fold in A8(c). P1 admission copies sorted/off from the addresses the layer's previous gate_up read
    (`core/place/stager.cpp:883-892`). In R Ulong, 87 of 111 final-chunk layers logged "admission orders moved";
    in C4 it was 111 of 111, with 0 admitted. Take the order from this pass's gate_up operands, or skip admission
    when they moved, and add a host test that reproduces a moved order.
  - Window: Ulong and Ulong8k with Kh, long Kld, N4/N8 unchanged, and a 96 GiB spill.
- **Effort.** M: 3-5 days, plus one window.
- **Files.** `core/place/card_expert_stager.cpp:894-915` (`add_drive`) and the DUnit/`by_unit_` lifecycle;
  `core/place/stager.cpp:883-892` (A8(c)); `tools/ds41-host-experts/ds41_p1.h` (a cap tunable);
  `tests/p1_stager_test.cpp`.
- **Risk.** Memory pressure: a 102 GiB cache collapsed under pressure before. Cap from MemAvailable, release
  carried planes on cancel, and do not starve the read pool.

### 6. Zero P1's cross-rank slot tail once per layer, not once per wave (A7)

- **Mechanism.** The P1 twin ends every call with `mx_tail_zero`. It writes zeros to the slots routed to other
  ranks, `[off[ne], T)`: contract T4, `libr4d/r4d_ds41_mxfp4.hip:2052-2054`, kernel at `:1623`.
  - `CardExpertPath::wave` relaunches the captured gate_up, SwiGLU and down for every wave
    (`core/place/card_expert_stager.cpp:709-750`).
  - Each wave therefore rewrites about 179 MB of zeros at M=2048: about 9,200 tail rows × (4,608 + 5,120) bf16
    columns, or about 0.3-0.4 ms at about 500 GB/s. At about 27 waves per layer, that is about 9 ms per layer
    when fully exposed.
  - In the Qa0 run, 2,826 of 4,180 waves found the ring full, so the card side was often the limit.
  - The fix lets only the wave replays skip the fill; the main launch keeps it.
- **Gain (corrected).** At Qa0 and 2K chunks: 6,817 tokens −2 to −5% alone, or −4 to −9% together with
  SWIGLU_SPAN (Qsp, which was neutral in the drive-bound pre-Qa0 regime, 17.22 vs 17.02 s). 3,086 tokens:
  about 0. 4K chunks: −4 to −7%. The gain grows if rank 5 removes drive waits.
  Qw4, which halves the number of waves, cut 6,817 by 3.4-5.1% but was 0.47% slower at 3,086. That fits a
  per-wave cost that matters at 6.8K.
- **Exact.** Yes, if only the wave replays skip the fill and nothing writes `[off[ne], T)` between the main
  launch and moe_gather.
  - Waves write only their own experts' slots, below `off[ne]`, and SwiGLU(0) = 0.
  - Down computes only live experts' slots. The only tail moe_gather reads is therefore down's, and only the main
    launch writes it.
  - Extend the p1 device check ("waves equal one launch", tail included) and reword T4.
- **First step.** In the p1 device check with `routes-long3086.bin`, time gate_up + down per wave on one card
  at M=2048 and 4096, with and without the tail fill. This needs only a checker build and runs in the next
  window's card checks. Kill the candidate if the saving is under 0.15 ms per wave. Then one window segment on
  Ulong8k at Qa0: base, tail-once, and tail-once + Qsp, with Kh.
- **Effort.** S: about a day, plus the device-check timing and one window segment. Build it together with
  rank 5.
- **Files.** `libr4d/r4d_ds41_mxfp4.hip:1919` (`MxP1Opts`), `:2011-2054` (the P1 branch and T4), `:1829`
  (`mx_tail_zero`); `core/place/card_expert_stager.cpp:709-750` (`wave`);
  `tools/ds41-host-experts/ds41_mxfp4_device_check.hip` (p1 mode); `tests/r4d_emu/test_ds41p1.cpp`
  (`waves_case`).
- **Risk.** Low: a new option bit and new wording for T4.

### 7. Two-batch overlap v2: per-lane MoE buffers (B4)

- **Mechanism.** v1 (`core/sched/tbo.h`) splits a decode step into two micro-batches but keeps the MoE's
  pass-tall buffers shared, so B's router runs only after A's gather. v1's own counters show the idle gaps this
  left (ab-20261030T231526Z, rank 0, per micro-batch). v1 lost 3-5% overall.

  | Streams | Counts wait (µs) | Gather wait (ms) |
  |---|---|---|
  | 4 | 598 | 0.633 |
  | 8 | 887 | 1.259 |

  v2 gives each lane its own decode-sized MoE buffers, so that B's routed work overlaps A's CPU burst. The stager
  then holds two passes in flight per rank.
- **Gain (corrected).** In CW, rank 0's chain takes 0.50 / 0.92 / 1.38-1.43 ms per layer at N1 / N4 / N8, and the
  gather waits are 1.556 ms (N4) and 2.977 ms (N8).
  - Pool-bound ceiling: −20 to −25% step time at N8.
  - Card-bound floor: about 0 at N4. With 2-row lanes, twice the 2-row chain is about 1.3-1.7 ms, against a
    1.56 ms 4-row pool burst.
  - The counters cannot tell which of the two applies. Planning number: +5-15% at N8, 0-10% at N4.
- **Exact.** Yes, by v1's argument. Each micro-batch issues the ops of a step of its rows alone, neither one reads
  bytes the other wrote, and rows are independent. Only buffer separation and issue order change.
  `tests/ds41_tbo_arch_test.cpp` must cover the unshared lanes.
- **First step.**
  - The no-build trace pair (measure-first item 2): N8 Ct16 against Ct16 + Tb, on the decode-only profile.
  - Go only if two conditions hold: Tb's card is at most 70% busy, and twice the per-lane chain plus resident
    GEMMs at 4 rows is at most 0.8x the 8-row pool burst.
  - Before the pair, CPU only: check `chain_report.py`'s `SYNC_OPS` (`:33`) against ds41's MoE op
    (`arch/common/rad_block_moe_fp8.h:892` declares `moe_scatter`).
  - Also CPU only: microbenchmark rank-thread wake latency under a busy 40-worker pool (target at most 50 µs;
    the MWAITX lesson).
- **Effort.** L: 2-3 weeks.
- **Files.**
  - `core/sched/tbo.h`.
  - `core/build/rad_builder.cpp`: v1 unshares every transient arena buffer. That was cheap at 16 rows (9.52 vs
    8.22 MiB), but the 2,048-row arena is about 935 MiB, so v2 must unshare only the per-lane MoE buffers.
  - `core/place/stager.cpp`: the `hx_early_decide`/`hx_finish` state, read-ahead and multi-row read-ahead
    accounting for two passes in flight.
  - `core/place/host_expert_pool.*`; `arch/deepseek41/deepseek41.cpp`.
  - Tests: `tests/ds41_tbo_arch_test.cpp`, `tests/tbo_stager_test.cpp`.
- **Risk.** High, through interplay with Ei, read-ahead and rank-thread wake under load. The DSpark "verify
  lanes" idea (B1, dropped) is this same implementation used for one stream.

### 8. Row-aware P1 read-ahead (B6)

- **Mechanism.** P1 reads ahead the next layer's top 8 non-resident units by profile share
  (`core/place/stager.cpp:5032-5040`).
  - At Qa8, 512 useful prefetches cut drive waits only on rank 0 (4.824 → 4.136 / 3.779 s). On ranks 1-3 the
    waits moved by −0.14 / +0.03 / −0.19 s.
  - Meanwhile ready-slot waits rose to 1.6-3.2 s, against 0.05-0.85 s at Qa0. That is why Qa0 won.
  - The fix picks prefetches by expected rows (a λ threshold) and lets a prefetch yield its ready slot to a demand
    unit.
- **Gain (corrected).** 0 to −4% long-prompt TTFT against Qa0, out of an 18.46 s P1 wall. Rank 5 removes many of
  the same reads, so re-score this after rank 5.
- **Exact.** Yes. It changes only which units are read early (I/O).
- **First step.** Run an offline replay; the live route trace is refused under P1 (`stager.cpp:4688`).
  - Inputs: the Oct 29 Ulong trace (`rtrace-...-Rt-Lm4096-Ulong/rt.rank0.bin`, read with `rtrace.py`) and the new
    6.8K trace, at the 2,048 / 1,038-row chunks and the cut heights.
  - Compare today's top 8, the λ rule, and yield-to-demand.
  - Build only if one rule keeps at least 70% of useful prefetches and drops at least 70% of wasted ones.
- **Effort.** S for the replay; S-M for the build.
- **Files.** `core/place/stager.cpp:5032-5040`; `core/place/card_expert_stager.cpp:951` (`read_ahead`);
