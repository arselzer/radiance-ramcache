Bounded immutable HOST RoPE table store (standalone planning helper)
=================================================================

ds41_rope_tables.h uses the existing ds41_transform_table.h build_pairs and
select_spec. It does not change their equations, register an operator, upload a
table, integrate an architecture graph, or establish a 262K model memory fit.

API (namespace rad::ds41::transform):

  RopeTableStore store({payload_byte_budget, maximum_live_table_count});
  RopeTableStore::Lease table;
  int status = store.get(spec, requested_positions, &table);
  std::span<const float> pairs = table->pairs();
  auto accounting = store.accounting(); // read-only lifetime/accounting handle
  store.clear_unleased();

Lease is std::shared_ptr<const RopeTable>. The table's spec, key, receipt and
payload are immutable through this API. Pairs have the existing position-major
[positions, rotary/2, 2] interleaved cosine/sine layout. There is no independent
second full table copy: build_pairs constructs its result vector, and vector
ownership moves into the table. No vector capacity/pointer is exposed as mutable.
The initial store/ledger construction can throw std::bad_alloc. get translates
payload/table/control-block/map allocation failure to RAD_E_NOMEM and length
failure to RAD_E_SHAPE; failed calls leave the caller's replacement lease intact.

Keys and supported environment
------------------------------

A key contains EVERY RopeSpec field: rotary, original_context, the exact IEEE
F32 bits of theta/factor/beta_fast/beta_slow, requested position count, and the
algorithm version. Version1 identifies this build's existing build_pairs path;
other versions are refused. Fields are included even if a particular branch
does not use them. This is an in-process key, not a cross-build persistent cache
or a promise that different libm/compiler implementations produce identical bits.

All shape/spec/checked-size validation and a host floating-point environment
check precede any allocation or hit return. The environment must have F32 IEEE
storage, FE_TONEAREST, and working normal-to-subnormal and subnormal-to-normal
arithmetic (no FTZ/DAZ). A fast-math/finite-math-only build refuses this helper.
Each calling thread must keep its floating-point CONTROL settings unchanged
through the call. Probe arithmetic can set floating-point exception status
flags; it does not modify control settings. No assumption about a GPU environment
follows from this host check. GPU table upload/read lifetime remains separate.

Budget/lifetime and concurrency
-------------------------------

Both limits apply to this ONE store's shared accounting ledger. Payload means
exactly positions * rotary * sizeof(float), counted in logical float bytes.
Allocator rounding/vector spare capacity, map nodes, synchronization objects,
control blocks, the bounded builder's stack scratch and caller-held lease objects
are excluded. The entry cap bounds live payload objects/reservations and the
strong-entry map. A zero cap refuses cold construction. Metadata/overflow is
checked before reserve/allocation, and a reservation is included in both counters
before build_pairs starts. Allocation or arithmetic refusal refunds after any
temporary vector has been freed.

The store keeps strong map entries and deliberately has no automatic eviction.
Cold construction is serialized under the store mutex, including table math;
same-key callers cannot race two constructions. Hits also wait for that mutex.
This favors a small safe baseline over parallel construction. clear_unleased
only releases a map owner observed as the sole strong owner. Existing readers'
table memory is never overwritten/reused. Each entry also has a weak identity:
if an external weak_ptr promotion races that release, the key stays in the map,
and the next get restores its strong owner with the SAME immutable table. An
expired identity is removed by clear or before admitting another cold entry.
Thus weak promotion cannot create two live same-key payloads. Weak-only retained
identities correspond to charged live payloads; expired nodes are pruned before
admission, keeping metadata entry count bounded by the same entry cap.

Table destruction physically frees its vector before releasing bytes and its
entry charge. A separate ledger is shared by store and tables, but owns neither
the map nor any table, preventing a map/table/deleter cycle. Destroying the store
releases its strong map owners; surviving external leases retain valid data and
the full charge. A read-only accounting handle can observe that charge but does
not itself retain table payload. Ordinary C++ lifetime rules apply: do not destroy
a store while another thread is executing its methods. Independent lease use and
release are safe across threads after get returns and after store destruction.

The budget is not implicitly global across separate RopeTableStore instances.
Future architecture code must own one shared store for the model (or explicitly
partition a global budget); it must not silently grant the full budget to each
layer, rank or independent store. Device copies need their own cap and stream /
event / replay lifetime ownership.

Provenance and tiny tests
------------------------

The real relevant config values in ds41_rope_tables_test.cpp are copied from:
  deepseek-ai/DeepSeek-V4.1-Flash-1017, HF revision
  1bae0e1088993b9b82de08f59de5be5a34e42170
  config.json SHA256
  8be45ce0476004a3f529fd896115a4a2e800a129ad2d3ec05b16050f52e21879.

Its 40 backbone layers select two specs via the real select_spec:
  layers0/1: rotary64, theta10000, original_context0;
  layers2..39: rotary64, theta160000, original_context65536;
  both: factor16, beta_fast32, beta_slow1.
The C2/C1 distinction does not create a third RoPE specification. Tests request
only EIGHT positions, two 2048-byte payloads. No test requests full model tables.
Nine CPU test cases cover two-spec identity, exact complete keys, byte/entry
caps, explicit clear, replacement atomicity, post-store lease/charge lifetime,
12-thread same-key dedup, invalid/overflow/zero caps, late builder arithmetic
failure reservation cleanup, rounding-mode refusal and x86 FTZ/DAZ refusal.
The final test checks deterministic promotion-before-clear and clear-before-lock
endpoints plus1022 bounded weak-promotion races, verifying identity under the full
128-byte/one-entry quota. The narrow use-count/reset interleaving is stressed,
not deterministically forced. Stop-aware gates release a worker on early test
failure; the multiworker dedup test uses a construction-failure-safe start latch.
Allocation-failure refund stages were source-reviewed, not fault-injected.
These are ownership/bounds tests using existing math, not independent new RoPE
numerical goldens, graph integration or model-quality validation.
