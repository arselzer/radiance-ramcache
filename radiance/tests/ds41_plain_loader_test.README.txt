Actual Engine load-time BF16 -> F32 proof (HOST)
===============================================

The parent explicitly approved the actual source-derived conservative bound:
up to640MiB requested pools+bounce, plus <=2MiB logical source/staged bytes and
separate runtime/allocator/thread-stack overhead. RelayoutPool additionally
reserves4GiB anonymous virtual address space; this is not4GiB committed RAM.
This is an explicit integration/slow CPU run, not an ordinary fast-suite case.
No production loader defaults were changed. No child run has occurred; execution
claims below describe intended assertions until the parent runs the binary.

This test uses tiny::write_qwen35 with two existing supported layers, context64,
hidden64 and the real qwen35_bf16 architecture / libref kernels. It calls public
Engine::start(), never Engine::serve(), opens no HTTP listener and submits no
request. The existing graph declares output_norm.weight as F32, although the
generated model.language_model.norm.weight checkpoint payload is BF16.

The test reads the generated BF16 bytes independently, lets the real private
StagedWeight::run loader convert them, and checks the actual Engine-owned F32
destination pointer bit for bit against uint32_t(source_bf16_bits)<<16. It also
checks widen=true, source encoding BF16 retained, declared/stored dtype F32,
four stored bytes/value, identity plain layout and unchanged checkpoint bytes.
There is no manually converted payload, source pointer rebinding, stub loader,
new architecture, kernel implementation or launch replacement.

The source is a rank1 norm. This proves the actual Engine widening branch and
its ownership/publication for that supported graph; it does NOT claim actual
DS41 C2/router rank2 matrix load/execution, GPU/AQL, inference, TP, speed, quality
or full-model memory capacity. The earlier ds41_plain_projection_runtime_test
separately checks real HOST GEMM consumption of a manually widened rank2 tensor.

Bounds and isolation:
 - main hides GPUs before its first explicit device query; test requires actual
   HOST backend plus exactly one synthetic device. Linked HIP registration can
   occur before main in a HIP-enabled binary; no constructor suppression claim.
 - synthetic HOST VRAM128MiB; maxctx64, maxseq1, maxbatchedtokens64, TP1;
 - no host weight pool, no prefix cache/snapshots/speculation/prefetch; embedding
   explicitly in the device (HOST-backed) weight pool; all_vram static placement;
 - generated checkpoint is capped at512KiB before reading it for assertions;
   before Engine.start, four complete file copies plus per-source4096-byte
   rounded staging must total<=2MiB logical requested bytes;
 - actual loader worker count is computed by the same2..16 formula as Engine;
   each worker lazily requests a32MiB pinned bounce ring. Preflight prints the
   worker-bound receipt and requires128MiB device/pools plus these rings<=640MiB;
 - GPU headroom16MiB is an explicit CPU fixture budget, not production guidance.
Engine reserves4GiB anonymous staging VA, touching only the tiny used input
range; MADV_HUGEPAGE/page rounding can change physical commitment. These logical
byte bounds are not an exact RSS/locked-page estimate. The128MiB synthetic device
figure alone is not the loader footprint; the full conservative bound above is.
Thread stacks, argument/stream queues, plugin/runtime/allocator metadata and
shared-library mappings are explicitly separate. This test does not hard-limit
the process address space and does not use RLIMIT tricks to alter loader paths.

Build integration required (parent-owned):
 - source links the real rad_core (which includes Engine); use the same
   WHOLE_ARCHIVE rad_core + ENABLE_EXPORTS convention as radiance / the tests'
   RAD_TESTS_WHOLE_CORE list, because the architecture .so calls C ABI symbols
   back into this executable;
 - dependencies: qwen35_bf16 and libref; no libquant, rad-convert, DS41 module or
   radiance executable needed;
 - RADIANCE_HOME or RAD_TESTPLUGIN_HOME points at the built plugin home;
 - ordinary HOST CTest environment, no GPU entry or --run-gpu flag.
The source was handed off without child compilation/execution. Parent should
run this standalone CPU binary, then optionally the focused ASan/UBSan build.

Cleanup source review: Engine::start waits for RelayoutPool::finish(), whose
workers flush their bounce uploads before joining, before exposing a successful
return. Engine::~Engine drains mover transfers, shuts down each Ctx, frees step
state/ranks and closes plugins. The Engine lives inside the source directory's
lifetime; failed ordinary start/assertion unwinds the same RAII object. No serve
thread is started. This review does not prove handling of catastrophic device
loss or a process killed in the middle of allocation.
