Actual HOST projection-helper runtime gate

ds41_projection_runtime_test.cpp contains two CPU-only test bodies. Parent owns
test registration, builds and execution. It needs actual libquant/libds41_ref
build dependencies, the ordinary rad_core HOST backend, and the existing
RAD_GOLDEN_FIXTURES compile definition. Compile this test with -ffp-contract=off,
matching libds41_ref's separate F32 multiply/add contract. It does not use ds41meta launch stubs,
replace a registered launch, initialize GPUs, create Pools, load full weights,
or touch a service. Intended runtime is under10 seconds on the development host;
this source-only handoff does not assert a measured execution time.

The first body tests issue_native_linear through actual Builder/Ctx/rad_issue
and libds41_ref for all six supported GGUF formats. Input has two F32 token rows;
each generated weight is4x256 and the output is BF16. Numeric expectations come
from the checked-in independent GGML f32 goldens, not the DS41 packed emulator.

The second body tests mixed IQ2_XS gate / IQ3_XXS up / Q5_K down experts, hidden256,
FFN1280, topk2, two tokens and four route jobs. It executes logical TP4 ranks
sequentially on one host device. Layer2 rotates the wide512-element shard onto
rank2; the other ranks own256 elements. Full source matrices contain five256-wide
blocks and row/chunk-dependent exact powers-of-two scales so a wrong row span or
down-column span changes both expected raw blocks and numeric answers.

Gate/up issue M=2 with input token-row mapping [1,0,1,0] and canonical expert IDs
[1,0,0,1], producing four output rows each. The down helper must issue M=4 through
its maxRoutes range, consume four BF16 activation rows, and use identity row IDs
[0,1,2,3]. Its output is F32 per-job partials. This deliberately catches the
maxTokens/maxRoutes confusion which declaration-only tests cannot exercise.
All helper return values and all four per-job statuses are checked, in addition
to Ctx success, unchanged inputs/native records and numeric outputs. An explicit
helper over-capacity request must refuse and leave output unchanged.

Canonical source-to-payload composition is exercised beyond hand-constructed
rank-local bytes:
  generated valid native source records from independent golden rows -> real
  libquant importer -> generic Core canonical decode checked against the golden
  numeric values -> actual encoding/source name map -> helper declarations ->
  actual Builder private dtype/layout/all-plane selection -> actual Core
  weight_share rectangles for each uneven ROW/COL source slice -> weight_planes
  descriptors -> resolved real registered relayout -> exact comparison with an
  independent slice of the original native source bytes -> real Ctx weight/table
  binding and unmodified HOST projection launches.
The selected-plane rectangle copy mirrors Engine's fill/staging composition;
it does not invoke Engine, on-disk container/checkpoint loading, sweep workers,
O_DIRECT, real file offsets or mover publication. Those I/O paths remain separate
integration gates. Native buffers have256-byte guard regions and256-byte-aligned
payload starts; their entire original allocations must remain unchanged.
Program-sized actual HOST/device arena arithmetic is capped at1MiB per fixture;
each native record is capped below1MiB. Full generated sources are small metadata
fixtures, not downloaded model tensors. No graph KV/state/cache allocation occurs.
An independent metadata-only Python check confirmed that every golden half scale
used here (including zero and the smallest subnormal) supports the requested
exact power-of-two upward shifts0/1/2. The C++ generator checks the same profile.

HOST test scaffolding supplies SiLU(gate)*up*route_weight activations between
projection calls, rounded once to BF16. It explicitly does not declare or prove
the actual expert_act graph/kernel, clamp semantics or a production asynchronous
activation hand-off. Gate/up outputs are independently checked before that
scaffolding's consequences are accepted. Source weights and input values are
finite; special NaN/overflow numerical policies are outside this fixture.

Finally the CPU test sums F32 down partials across logical ranks PER EXPERT JOB,
casts each completed expert once to BF16, then combines in ascending expert-ID
order per token. Independent expected local dot products use the golden logical
weights and identical explicitly stated rank reduction order. A distinguishing
assertion requires at least one value to differ if partials were cast per rank.
This is a mathematical hand-off check, not an actual all-reduce/gather, multi-rank
runtime, communication accuracy/performance test or full DS41 architecture proof.
HOST reference accumulation is ascending K with separate F32 multiply/add; GPU
wave reduction may differ. No GPU bit-equality or throughput claim follows.
